## 4. IR-D5BC10-RR4-01 — HIGH, blocking: actual terminal latch can predate first-error/state snapshot, yielding a falsely healthy P5 entry

The source-level definition of **terminal business execution** is broader than the two fields in slot 4. [`TerminalMethodDenied`](https://github.com/night-outlook/il2cpp_plus/blob/e9aee83345aa9df90085de50162a7aa9172e8263/libil2cpp/vm/AssemblyShadow.cpp#L325-L336) checks **four durable failure conditions**: `s_typeFailure`, `s_unexpectedFailure`, `s_lateBaselineUse`, `s_referenceViolation`, plus `s_state`. But [the RR4 target-entry hook](https://github.com/night-outlook/il2cpp_plus/blob/e9aee83345aa9df90085de50162a7aa9172e8263/libil2cpp/vm/AssemblyShadow.cpp#L2324-L2349) records only `s_state` and `s_firstFailureV2.status`. It does **not** record whether any durable latch was already present when the target method entered.

This gap is **reachable by the actual source publication order**, not merely a hypothetical malformed receipt. [`RecordFirstGuardFailure` lines 268–281](https://github.com/night-outlook/il2cpp_plus/blob/e9aee83345aa9df90085de50162a7aa9172e8263/libil2cpp/vm/AssemblyShadow.cpp#L268-L281) publishes `s_typeFailure` through a successful atomic CAS **before** the winning writer calls `s_firstFailureV2.TryFreeze`. Terminal state is assigned later on relevant failure paths. During the widened P5 window, this valid interleaving is possible:

1. Native state is `Committing (5)`, first-error state is `Empty (0)`; a competing failure writer successfully CAS-publishes `s_typeFailure`, then is preempted before `TryFreeze`.
2. The one-shot TLS-bound `Keep` guard enters: RR4 slot 4 records `(1,1,5,0)` as **healthy** even though `s_typeFailure != nullptr` already makes business execution terminal under the production policy.
3. `TerminalMethodDenied` sees that published durable failure, returns true, and `WindowProbe::MethodResult` reports target denial in P5.
4. The competing failure writer then freezes the first error and sets `FailedAfterCommit (9)`. The collector can record terminal state 9, frozen first error, unmodified canary and native denied result. [The parser](https://github.com/night-outlook/hybridclr_demo/blob/54cd6c3d6c8cc313d00c542d15f0bb409aafbe09/Tools/AssemblyShadow/R03IR/D5Probe/d5_c10_native_receipt.py#L104-L148) considers state=5/firstError=0 at entry sufficient for `HealthyP5CommittingFirstErrorEmpty`, so a **pre-poisoned terminal rejection may be classified** `CandidateObservedDeniedInP5_RequiresIndependentBinaryProof` if the remaining source-material/PID/exit fields agree.

This does not prove an observed Player false positive; it demonstrates a **real source-order counterexample** to the claim that RR4 establishes a healthy P5 guard-entry policy. The host `entry_preterminal` and `entry_prior_error` tests inject only already-updated state/error values. They **never** test the split interval where a durable latch is set but those two fields still look healthy.

**Required Primary correction:** instrument the *same effective terminal predicate* used by `TerminalMethodDenied` at the exact bound target entry, including durable latches, and distinguish **preexisting terminal, failure racing the guard, and healthy P5 business-policy denial**. Preserve first-error B1 immutability. A noncoherent mixed state/error/latch read must fail closed or be labeled raced/unknown—not claimed healthy by comparing only two atomics. Add a host interleaving where `s_typeFailure` is published first, `s_state=Committing`, `firstError=Empty`, and only later first-error/terminal state update. Verify no healthy-denial candidate can be produced by that sequence. Do not blindly prohibit all `Committing` calls globally; the desired product policy still requires separate real-VM validation.

## 5. IR-D5BC10-RR4-02 — HIGH, blocking: release/acquire observation is not authenticated as completion of the target worker

[`WindowProbe::ReleaseP5`](https://github.com/night-outlook/il2cpp_plus/blob/e9aee83345aa9df90085de50162a7aa9172e8263/libil2cpp/vm/AssemblyShadowD5WindowProbe.h#L96-L115) checks **only** phase==AtP5 and performs a global `release_` CAS. It does not check which thread called, whether it owns the exact TLS-bound `Keep` attempt, or whether the method body has returned. [The test C ABI `R03_D5_ReleaseP5Window`](https://github.com/night-outlook/hybridclr_demo/blob/54cd6c3d6c8cc313d00c542d15f0bb409aafbe09/Tools/AssemblyShadow/R03IR/D5Probe/R03D5WindowOverlay.cpp#L425-L433) forwards that call unconditionally. The intended [C# worker](https://github.com/night-outlook/hybridclr_demo/blob/54cd6c3d6c8cc313d00c542d15f0bb409aafbe09/Tools/AssemblyShadow/R03IR/D5Probe/R03D5P5WindowPlayer.cs#L105-L127) releases in its `finally` after `Invoke`; that intention is source-visible, but **the native API does not enforce it**.

The [native collector](https://github.com/night-outlook/hybridclr_demo/blob/54cd6c3d6c8cc313d00c542d15f0bb409aafbe09/Tools/AssemblyShadow/R03IR/D5Probe/R03D5WindowOverlay.cpp#L239-L249) uses `decision==1 && HasWorkerCompletedP5Acquire()` to permit raw, non-atomic `R03.Node.stable` reading. If a separate thread calls the exported release while the admitted target method is still executing, the release/acquire pair synchronizes with **that other thread**, not with the actual worker's in-progress field writes. It can therefore permit an unsynchronized raw canary read and produce a false `nativeP5ReleaseObserved` implication of worker completion. No actual concurrent real-VM memory race was observed in CI; this is a source-level conditional interleaving. The [host `canary_happens_before` case](https://github.com/night-outlook/hybridclr_demo/blob/54cd6c3d6c8cc313d00c542d15f0bb409aafbe09/Tools/AssemblyShadow/R03IR/D5Probe/D5WindowSourceHost.cpp) tests a *correctly ordered writer* only, not wrong-thread release.

**Required Primary correction:** bind release/finished-body publication to the **same exact target worker identity** and a real post-invoke native completion boundary, or independently prove exclusive ownership within the isolated Player with a fail-closed check enforced at the native export. Add negative host case: worker arms + enters + target guard allowed but remains in an in-progress body; another thread calls `ReleaseP5`. The early external release must **not** allow `HasWorkerCompletedP5Acquire` to become true or the collector to read the canary. Keep timeout bounded and do not use a managed post-terminal `Join` or read-only GC callback.

## 6. IR-D5BC10-RR4-03 — MEDIUM, safety-significant: canary-unreadable path can hide a native P5 guard admission

The [collector](https://github.com/night-outlook/hybridclr_demo/blob/54cd6c3d6c8cc313d00c542d15f0bb409aafbe09/Tools/AssemblyShadow/R03IR/D5Probe/R03D5WindowOverlay.cpp#L233-L252) sets `valid=0` if the native canary read fails, even after a same-token guard returns `Allowed` and the release flag is observed. [Its exit selection](https://github.com/night-outlook/hybridclr_demo/blob/54cd6c3d6c8cc313d00c542d15f0bb409aafbe09/Tools/AssemblyShadow/R03IR/D5Probe/R03D5WindowOverlay.cpp#L380-L393) can still choose **42** for native `decision==1`. Yet [the parser's global `joined` predicate](https://github.com/night-outlook/hybridclr_demo/blob/54cd6c3d6c8cc313d00c542d15f0bb409aafbe09/Tools/AssemblyShadow/R03IR/D5Probe/d5_c10_native_receipt.py#L116-L148) requires `observed[10][1]==1` and `bound==1` **before** reporting `UnsafeEarlyMethodAdmissionObserved_SourceMaterial`. If the VM canary proves unreadable or unbound *after* guard admission, a genuine exact-target `Allowed` guard/exit42 can be reduced to `NoCoverage` rather than preserved as a critical guard-admission signal.

This is a **classification blind spot**, not a claim that any real canary failed: the complete real-VM branch has never been compiled or run. The [D5-C10 planned matrix](D5_LOCAL_VALIDATION_MATRIX_2026-11-20.md) treats **method admission before the initializer policy permits it as a critical failure**, independently of whether the body-side-effect canary is readable. The existing host allowed profile always supplies a valid synthetic canary and does not test this condition.

**Required correction:** separate **exact same-token early guard admission** from the weaker claim that the body mutated its side-effect field. Preserve an explicit critical/suspicious `AllowedGuardAtP5_CanaryUnknown` source-material result when the guard/entry/counters/exit are authentic but canary is not readable; do not fabricate body execution. Add a negative/critical host case where native `decision=1`, target entry healthy, `ReleaseP5` observed, but slot9/10 after-canary validity is 0. The parser must not silently downgrade the observed admission to generic `NoCoverage`. Any future real-Player decision still requires independent binary/PID/argv identity.
