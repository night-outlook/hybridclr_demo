# R03 D5-B prospective Local dry-admission — focused R2 design amendment

**Date:** 2026-11-24 UTC. **Status:** Primary implementation / source-only CI complete, **separate independent R2 review pending**. This amendment responds only to [independent D5-B physical dry-admission `ReturnRequired`](D5B_LOCAL_DRY_ADMISSION_INDEPENDENT_REVIEW_2026-11-24.md), findings `D5B-DRY-IR-01/02/03`. It supplements rather than retroactively rewrites [the original D5-B design](D5B_LOCAL_DRY_ADMISSION_DESIGN_2026-11-24.md). The prior `D5BRR5R2IndependentReview=PassSourcePreflightOnly` remains valid solely for Git-source preflight. **No Local command, Unity, IL2CPP or Player execution is authorized here.**

## 1. IR-01 — immutable raw-approval authentication at the actual writer

The old direct `seal_oneuse_dry_admission(approved: dict, admission: dict)` accepted arbitrary approval dictionaries when a test-only future non-null approval constant was supplied. The revised sole writer is `seal_oneuse_dry_admission(approved_raw: bytes, admission: dict)`: it calls `approved_envelope(approved_raw)` **inside the writer**, before any directory creation, to verify the exact immutable reviewed envelope **Git blob**, all approval/branch/commit/path/Unity SHA and `NoUnityOrPlayerLaunch` constraints. It constructs the request from the authenticated envelope itself, calls the full `inspect(request)` to regenerate actual physical evidence and rejects mismatch against the caller's earlier inspected snapshot. Passing an untrusted dict or mutated bytes cannot produce output. The public CLI also checks raw approval on entry, but no longer relies on that caller-side check as its sole authorization.

Current published code intentionally retains `APPROVED_EXECUTION_ENVELOPE_BLOB=None` and the proposal's null approval fields. Tests temporarily patch this constant only inside synthetic, isolated Python test processes. A passing synthetic approved-envelope regression is **not** a user approval or a released handoff.

## 2. IR-02 — bound physical directory descriptors and repeated source custody

An approved one-use dry admission must consume the exact frozen four-repository Git SHA tuple, the historical Original S checkout and all six historical custody roles, the Unity binary SHA and the external absent one-use output. The revised `inspect`/`check_custody` record `(st_dev, st_ino)` identities for the proposed external parent, all historical roots and four source roots. The `seal` boundary repeats the **full** source/remote/Original-S/host inspection before writing, comparing stable source and path fingerprints to the caller's prior observation. The output parent is then opened via `os.open(O_RDONLY|O_DIRECTORY|O_NOFOLLOW)` and checked against the prior device/inode; `os.mkdir(..., dir_fd=parent_fd)` creates a single one-use child and `os.open(..., dir_fd=parent_fd, O_NOFOLLOW)` binds the child descriptor. Receipt files are written exclusively using `openat` semantics (`O_EXCL|O_NOFOLLOW`), `fsync` and the bound child descriptor, **not reopened via a mutable user-provided pathname**.

After preliminary `ADMISSION.json` and `CELLS.json`, a new `inspect(request, expect_output_present=True)` rechecks actual source bytes/clean local HEADs, all four **live** remote branch refs, R2 ancestry, original S and physical parent/history/source identities; the output must now be the exact canonical directory. The writer records `POSTFLIGHT.json`, rechecks source and directory identity again, hashes the actual preliminary receipts, and writes `MANIFEST.json`. A **final** full source/host/historical recheck runs after the durable manifest and immediately before the final exclusive `LOCAL_BATCH_RESULT.json` success marker. Any failed recheck must not emit a positive batch receipt.

These checks close the reviewed source-path alias/replacement and stale source-at-writer gaps within the prospective **read-only dry receipt** scope. They do not supply an atomic cross-repository Git snapshot against a concurrent adversary outside the process, nor establish a real linked Player; such limitations remain separate future environment/evidence review topics. The committed code is not executable while the approval anchor is null.

## 3. IR-03 — factual partial-output reporting and one-use consumption

The one-use root may be created **only after** authenticated raw approval and successful refreshed inspection. The writer tracks whether `mkdirat` succeeded. Once created, any subsequent exception becomes `PartialOutput`, **never** an ordinary pre-output denial. The consumed output root is not deleted or retried. Where filesystem space permits, the writer attempts an exclusive `FAILURE.json` record in the bound directory, including the failure reason and a ledger of physically present completed receipts. The CLI reports `result=FailedAfterPartialOutput`, `outputCreated=true`, `retryAllowed=false`, the candidate path, observed file paths, SHA-256/byte-length ledger and whether the failure marker was written. If a secondary failure such as ENOSPC prevents even the marker, the truthful stdout receipt still states that the root was created.

The exclusive `LOCAL_BATCH_RESULT.json` is deliberately written **last**, after a manifest that includes the planned exact final-receipt hash; thus partial output or unsuccessful postflight must not be mistaken for a completed batch. The manifest never promotes a missing final receipt to real validation. All 18 D5 Player cases remain `NoCoverage`, with `realUnityBuild=NotRun`, and the one-use receipt never claims R03 acceptance.
