## 3. Findings requiring Primary correction

### IR-D5BC10-01 — HIGH, blocking: a constructor-guard outcome can be mislabeled as a successful C10 `Keep` denial

In [`R03D5P5WindowPlayer.cs`](https://github.com/night-outlook/hybridclr_demo/blob/a833d22487352135a88d6b245eea7f2d103af48b/Tools/AssemblyShadow/R03IR/D5Probe/R03D5P5WindowPlayer.cs#L103-L132), the worker resolves `R03.Node`, calls `Activator.CreateInstance(type)` **before** setting `attempted=true`, and only then calls `method.Invoke(instance,null)`. An active-shadow constructor or initializer can itself traverse a real method-entry guard (whether this happens must be confirmed by a Player). In [`AssemblyShadow.cpp`](https://github.com/night-outlook/il2cpp_plus/blob/8eeb3cc53a451a6925b490d623c81753822cb1d4/libil2cpp/vm/AssemblyShadow.cpp#L2324-L2461), the D5 witness counts **any** `MethodInfo` whose assembly is in `active->shadowToBaseline`, without binding the result to `R03.Node.Keep`. The managed [verdict predicate, lines 205–212](https://github.com/night-outlook/hybridclr_demo/blob/a833d22487352135a88d6b245eea7f2d103af48b/Tools/AssemblyShadow/R03IR/D5Probe/R03D5P5WindowPlayer.cs#L193-L213) only requires a worker that finished, observed P5, a nonzero native method-attempt counter and no timeout. It **does not require `shadowMethodInvokeAttempted`, a method-specific denial, or proof that `Keep` was entered**.

Consequence: a guarded constructor failure can produce `CandidateObservedDeniedInP5_RequiresIndependentBinaryProof` despite `Keep` never being attempted. This is a source-supported false classification of the **candidate** result, not an observed real Player outcome. Repair by separating object construction from the target method guard or recording an exact target-method identity and attempt/guard-decision join; a denied constructor must be a distinct `NoCoverage`/diagnostic outcome. Add deterministic regression coverage for constructor denial, `Keep` not attempted, and contradictory guard/managed counters.

### IR-D5BC10-02 — HIGH, blocking: C10's required real method-body side-effect witness is absent

The [D5-B producer/link plan](D5B_REAL_PLAYER_PRODUCER_AND_LINK_PLAN_2026-11-20.md) explicitly requires both **method admission/denial and a side-effect canary** for C10. The C# fixture observes `MethodInfo.Invoke` return/exception, `shadowMethodReturn` and generic native guard counters; it does **not** establish a pre/post canary for the target instance field, static field, or independently bound native observer. An `allowed` method guard is not equivalent to an actually executed body; a `denied` non-specific guard is not proof that the expected body did not run.

Add exact target-body precondition and postcondition evidence, preferably a pre-bound/native-readable primitive or equally independently authenticated witness that survives a possible terminal failure. Distinguish `AllowedGuard`, `BodyExecuted`, `BodyNotExecuted`, `NotAttempted`, `RacedP6` and `Unknown`; do not silently collapse these to a C10 verdict. Include a deliberately broken body-side-effect case and a positive healthy-control method-body case in focused tests.

### IR-D5BC10-03 — HIGH, blocking: terminal/exception output custody depends on managed execution after possible poisoning

[`R03D5P5WindowPlayer.cs` lines 193–234](https://github.com/night-outlook/hybridclr_demo/blob/a833d22487352135a88d6b245eea7f2d103af48b/Tools/AssemblyShadow/R03IR/D5Probe/R03D5P5WindowPlayer.cs#L193-L234) performs `CommitTransaction()`, `Thread.Join()`, `GetState()`, `JsonUtility.ToJson` and finally `FileStream(FileMode.CreateNew)`/`StreamWriter` **after** a worker's guarded invocation and potential `FailedAfterCommit`. The source-level terminal method guard can forbid ordinary AOT method execution in a poisoned process. The existing [historical `R03TerminalPlayer.cs`](https://github.com/night-outlook/hybridclr_demo/blob/a833d22487352135a88d6b245eea7f2d103af48b/Tools/AssemblyShadow/R03IR/PlayerProject/R03TerminalPlayer.cs) intentionally uses a fixed/native report writer to avoid precisely this post-poison managed I/O dependency. The new C10 writer silently catches any output exception (lines 223–232) and calls `Application.Quit(0)` independently of an unsafe or failed result. The worker also retains only the outer exception type, omitting possible `TargetInvocationException.InnerException` and first native failure.

This does not prove that the new writer fails in a real Player (no Player has run). It does prove that current source has **no fail-closed durable evidence path** for the crucial terminal/exception scenario. Add an authenticated, preopened exclusive native/fixed receipt path or equivalent evidence mechanism that does not rely on guarded post-terminal managed calls; independently collect native first-error, process exit/PID, target identity and timing. A missing/incomplete receipt must remain `NoCoverage` or `ReturnRequired`, not a clean exit inferred as a passing C10 control.

### IR-D5BC10-04 — CRITICAL runtime hypothesis, unresolved: phase P5 exposes active shadow while the method guard does not gate `Committing`

The new test-only [`AssemblyShadow.cpp` lines 1493–1544](https://github.com/night-outlook/il2cpp_plus/blob/8eeb3cc53a451a6925b490d623c81753822cb1d4/libil2cpp/vm/AssemblyShadow.cpp#L1493-L1544) enters P5 after `s_active` publication, calls `AtP5()`, deliberately unlocks `transaction.mutex`, holds the bounded window and later advances P6. The baseline [`AssemblyShadowTerminalExecution.h`](https://github.com/night-outlook/il2cpp_plus/blob/8eeb3cc53a451a6925b490d623c81753822cb1d4/libil2cpp/vm/AssemblyShadowTerminalExecution.h#L8-L27) treats only terminal state/durable failure as business-denied; `Committing` without durable failure is not terminal. [`RequireUserCodeAllowed`](https://github.com/night-outlook/il2cpp_plus/blob/8eeb3cc53a451a6925b490d623c81753822cb1d4/libil2cpp/vm/AssemblyShadow.cpp#L2518-L2524) tests staging/metadata-resolution scopes, not P5. Therefore, for a valid active-shadow `MethodInfo` and an otherwise healthy process, the source path does **not itself establish a P5 admission prohibition**.

That is a source-level policy risk, **not evidence that a shadow business body actually ran**. It predates this test-only witness and its production behavior has not been empirically established. C10 exists to test precisely this gap; do not mark the underlying runtime safe or defective based solely on synthetic counters. A valid producer must independently correlate actual phase, method guard decision and body effect; an actual early business body is critical `ReturnRequired`. Any future runtime policy correction must be designed separately so that legitimate P6 module initializer execution while `Committing` remains possible. Do **not** apply a simplistic global `Committing` denial or silently expand this review into runtime remediation.
