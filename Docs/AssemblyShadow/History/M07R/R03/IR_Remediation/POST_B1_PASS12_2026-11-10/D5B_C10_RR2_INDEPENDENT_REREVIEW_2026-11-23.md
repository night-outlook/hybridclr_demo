## 4. IR-D5BC10-RR2-01 — HIGH / blocking: early terminal-method denial has no target guard-decision receipt

[`AssemblyShadow.cpp` lines 2324–2341](https://github.com/night-outlook/il2cpp_plus/blob/87a34bbea39930dab96cf4703756d8da79d54684/libil2cpp/vm/AssemblyShadow.cpp#L2324-L2341) captures native P5 phase then **returns `false` immediately when `TerminalMethodDenied(method)` is true**. The exact target/`MatchesTargetOnCurrentThread(method)` computation occurs only later (approximately lines 2381–2402), and both `MethodResult` calls occur still later in allowed/failure branches. Therefore, an already-terminal process can reject the **actual bound target Keep method** without advancing `WindowProbe::TargetDecision`, without consuming the TLS token, and without producing native event slot 5.

The [autonomous collector, lines 261–316](https://github.com/night-outlook/hybridclr_demo/blob/38b166eea238ff7e734178175bfeaa33889a022d/Tools/AssemblyShadow/R03IR/D5Probe/R03D5WindowOverlay.cpp#L261-L316) requires a nonzero decision to write the method-result slot. It will eventually time out and produce incomplete/`NoCoverage` material rather than evidence of this real native rejection. This is fail-closed against a false pass, but the C10 producer is not complete at the requested method admission/**denial** observation boundary. The passing host cases fabricate `MethodResult(...,false)` rather than exercising the full early terminal-return branch.

**Required correction:** preserve the existing terminal policy while recording an **exact TLS-bound target denied decision** on the early return path without using guarded metadata resolution, allocation, locks or user callbacks; do not invent a new first-error or attribute a constructor to Keep. Add focused regression for early terminal denial distinct from ordinary validation/guard failures and P6 races. This is a **source-supported missing observation path**, not proof that the process reached that path in a Player.

## 5. IR-D5BC10-RR2-02 — HIGH / blocking: real pinned canary read lacks an established happens-before with the worker's field write

[`R03D5WindowOverlay.cpp` lines 130–145 and 154–181](https://github.com/night-outlook/hybridclr_demo/blob/38b166eea238ff7e734178175bfeaa33889a022d/Tools/AssemblyShadow/R03IR/D5Probe/R03D5WindowOverlay.cpp#L130-L181) uses native `memcpy` on `pinnedInstance->stable` from the detached collector. To allow that read following an admitted method, it tests `decision==1 && window.releaseCount==1`. But the actual [`WindowProbe::ReleaseP5 / Read`](https://github.com/night-outlook/il2cpp_plus/blob/87a34bbea39930dab96cf4703756d8da79d54684/libil2cpp/vm/AssemblyShadowD5WindowProbe.h#L95-L110) increments `releaseCount_` with `memory_order_relaxed`; [`WindowProbe::Read`](https://github.com/night-outlook/il2cpp_plus/blob/87a34bbea39930dab96cf4703756d8da79d54684/libil2cpp/vm/AssemblyShadowD5WindowProbe.h#L195-L218) also loads it with `memory_order_relaxed`. Observing that count does **not establish a C++ release/acquire happens-before** between the worker's non-atomic field mutation and the collector's raw field read. A pinned GC root prevents object relocation; it does **not** synchronize mutable field access.

A second timeout path can read non-atomic `canaryBefore` from [`FinishNativeReceipt`, line 180](https://github.com/night-outlook/hybridclr_demo/blob/38b166eea238ff7e734178175bfeaa33889a022d/Tools/AssemblyShadow/R03IR/D5Probe/R03D5WindowOverlay.cpp#L167-L181) **even when the `canaryReady` release/acquire publication has not been observed**. If the binder is concurrently publishing `canaryBefore`, this is another source-level data-race possibility. These concerns affect the **actual VM-only collector branch**, not the host mock, which reads `hostAfter` atomically and never compiles the pinned object access.

**Required correction:** add a real post-body completion release/acquire handshake (or an independently proven equivalent) before reading the non-atomic `stable` field; read `canaryBefore` only after the corresponding ready-acquire or make it atomic. Treat incomplete/timeout/raced observations as `Unknown/NoCoverage` without unsafe reads. Add concurrency-focused negative/positive source-host tests and make the future full VM/GC compile/runtime validation explicit. No actual data race was observed in the synthetic host logs; this finding is from unsynchronized source access.

## 6. IR-D5BC10-RR2-03 — MEDIUM / blocking evidence classification: the seal marker can be written even when durable completion fails

[`Record` at `R03D5WindowOverlay.cpp` lines 115–129](https://github.com/night-outlook/hybridclr_demo/blob/38b166eea238ff7e734178175bfeaa33889a022d/Tools/AssemblyShadow/R03IR/D5Probe/R03D5WindowOverlay.cpp#L115-L129) reserves the slot bitmap and uses `pwrite` **before** the corresponding `fsync`; a sync error may leave valid-looking slot bytes on disk and a failure return. [`FinishNativeReceipt` lines 210–217](https://github.com/night-outlook/hybridclr_demo/blob/38b166eea238ff7e734178175bfeaa33889a022d/Tools/AssemblyShadow/R03IR/D5Probe/R03D5WindowOverlay.cpp#L210-L217) writes the first-error block, then slot 10, then performs additional `fsync` and `close` operations. If the slot-10 write succeeded but its `fsync` or subsequent close fails, the fixed file **may already contain every required parsable slot** while the native function returns a failing seal outcome; the collector exits code 2.

The [Python classifier, lines 88–116](https://github.com/night-outlook/hybridclr_demo/blob/38b166eea238ff7e734178175bfeaa33889a022d/Tools/AssemblyShadow/R03IR/D5Probe/d5_c10_native_receipt.py#L88-L116) has no native seal-result or externally joined exact-process exit-status input. It treats a present slot-10 marker as a sealed source-material candidate, so a **complete-looking but failed-to-fsync/close** file can still receive `CandidateObservedDeniedInP5_RequiresIndependentBinaryProof`. This is not a real Player PASS—the parser always returns `realPlayerC10Passed=false` and the future external process-identity check is absent—but it weakens the claimed fail-closed native receipt contract. No native I/O fault-injection test closes this failure path.

**Required correction:** separate the durable-commit/close-success result from merely writing an event marker; require independently joined exact PID+exit evidence when classifying a complete native receipt for future admission, and add deterministic `pwrite`, `fsync` and `close` failures to host/synthetic tests. A failed sync/close must never look equivalent to a successful sealed candidate, regardless of file length/checksum.
