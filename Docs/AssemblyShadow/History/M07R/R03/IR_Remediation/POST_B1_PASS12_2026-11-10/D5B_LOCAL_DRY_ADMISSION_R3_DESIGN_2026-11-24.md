# D5-B prospective dry-admission R3 — durable one-use receipt protocol

**Date:** 2026-11-24 UTC. **Owner:** Primary Implementation. **State:** `R3SourceImplementationComplete_PendingIndependentReview`; no Local execution authorization. This focused amendment responds to [the independent D5-B R2 `ReturnRequired`](D5B_LOCAL_DRY_ADMISSION_R2_INDEPENDENT_REREVIEW_2026-11-24.md) and retains the predecessor [dry-admission design](D5B_LOCAL_DRY_ADMISSION_DESIGN_2026-11-24.md) and [R2 amendment](D5B_LOCAL_DRY_ADMISSION_R2_DESIGN_2026-11-24.md) as historical records. Scope is limited to **final receipt durability, descriptor-close outcome and fail-closed verification**, not D5-C/D5-D execution or native/Unity source changes.

## 1. Defect and acceptance contract

The R2 code used `_write_locked(root_fd, 'LOCAL_BATCH_RESULT.json', result)` as the final positive write. A complete JSON could be present with a matching pre-existing manifest hash even when its file `fsync` failed. Closing an output directory descriptor in a `finally` block could raise after an output had been created and reach the CLI's generic `outputCreated=false` handler. The R3 contract has two clear requirements: **no failed final write/durability step is structurally accepted as a complete one-use receipt**, and **all post-creation errors are reported with truthful consumption status and no automatic retry**.

## 2. Durability protocol and defined commit point

R3 adds an explicit durable failure-veto marker `INCOMPLETE.json` to a newly created one-use root before writing any positive material. The marker contains `result=NotCommitted`. Its file bytes and enclosing directory are fsynced *before* subsequent receipts. The writer exclusively writes and fsyncs `ADMISSION.json`, `CELLS.json`, `POSTFLIGHT.json`, followed by a `MANIFEST.json` v3 carrying the actual preliminary SHA-256/byte sizes and the **expected** positive final receipt digest. All operations use the already verified directory descriptor and `O_NOFOLLOW|O_EXCL` where applicable.

The positive result is first written under the **non-accepting** name `LOCAL_BATCH_STAGING.json`, flushed and fsynced; its bytes are then read back through the bound directory handle and compared with the exact expected JSON and manifest hash. The directory is fsynced to persist staged content. R3 performs the final source/live-ref/historical-parent reinspection and closes the parent descriptor **before** finalization. It then atomically renames staging to `LOCAL_BATCH_RESULT.json` in the same open directory and **fsyncs the directory while `INCOMPLETE.json` still exists**. Any write, close, rename or fsync failure before this point leaves an `INCOMPLETE` veto and therefore an invalid evidence product even if the renamed final file already appears on disk.

**Commit point:** only after the final file's parent directory fsync succeeds does the writer remove `INCOMPLETE.json` using the bound directory descriptor. The unlink is its *last visibility-changing disk operation*. A crash that loses the unlink can restore the veto marker, producing a **false negative** (not accepted), while a persisted unlink follows the already durably renamed receipt. There is intentionally no additional directory fsync after the unlink: such a fallible postcommit step would reintroduce an ambiguous returned failure after a complete-looking positive product. The protocol does **not** assert end-to-end platform crash consistency or real macOS validation from Linux host tests; real filesystem semantics remain a future separately reviewed Local concern.

An independent **read-only structure verifier** `inspect_dry_receipt_structure(root)` opens the physical directory with `O_NOFOLLOW`, requires **exactly** `ADMISSION.json`, `CELLS.json`, `POSTFLIGHT.json`, `MANIFEST.json` and `LOCAL_BATCH_RESULT.json`, and rejects **any** leftover `INCOMPLETE.json`, staging file, `FAILURE.json` or unexpected entry. It verifies manifest v3, per-file actual SHA-256/size, final JSON schema, 0 passed / 18 `NoCoverage`, `realUnityBuild=NotRun`, and `R03Accepted=false`. This result is named `SealedDryReceiptStructureOnly_NotLocalAuthorization`: it never supplies approval authority, real BuildPipeline output or Local evidence acceptance.

## 3. Descriptor cleanup is inside root-created-aware reporting

R3 eliminates the R2 unconditional `os.close` in a `finally` that could override a return or partial-output error. The parent descriptor is deliberately closed *before* the atomic final commit; any close failure leaves `INCOMPLETE.json`, and the evidence root is consumed/recorded as a partial failure. A root descriptor close **after** successful final marker publication is captured rather than allowed to propagate into the generic `outputCreated=false` exception handler.

If any precommit step fails after `mkdirat`, the output is retained and marked `FailedAfterPartialOutput`, `outputCreated=true`, `retryAllowed=false`; an exclusive `FAILURE.json` with available on-disk hashes is attempted. Under ENOSPC even the failure marker may not be writable, but the incomplete veto remains. If the final unlink already committed and the root descriptor subsequently fails to close, the CLI returns **`IndeterminateAfterCommit`**, `outputCreated=true`, `commitVisible=true`, `requiresPhysicalReconciliation=true`, `retryAllowed=false`, and cleanup diagnostics. A structurally valid on-disk product in that case is **not** silently treated as a green Local batch: an independently verified command outcome is still required at a later Local evidence gate.
