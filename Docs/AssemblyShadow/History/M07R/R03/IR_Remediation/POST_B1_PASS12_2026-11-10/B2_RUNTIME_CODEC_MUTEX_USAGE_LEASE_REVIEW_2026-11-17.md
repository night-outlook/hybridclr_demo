## 1. Findings from the pinned implementation

The preceding [transitive publisher review](B2_TRANSITIVE_PUBLICATION_MUTEX_CHAIN_REVIEW_2026-11-17.md) traced `transaction.mutex → g_MetadataLock → s_assemblyLock → UsageLock → reservationMutex → codec.mutex_`. This cycle examines the two rightmost mutexes and the cross-callback `UsageLock` ownership more narrowly.

At the pinned `hybridclr/metadata/InterpreterMetadataIndexRuntime.cpp` blob `509e357359a8912c05adac3434a7e71b3fc3f83c`, **six** direct `reservationMutex` acquisitions are identified: `Initialize`, `ReserveImages`, the two `ScopedConstruction` overloads, `PublishBatch`, and `Abort(uint32_t)`. `ReserveImages`, `PublishBatch`, and `Abort(uint32_t)` call the codec while owning that mutex. `Runtime::GetStats` goes directly to the codec, **without acquiring reservationMutex**. The `hybridclr/metadata/InterpreterMetadataIndexCodec.h` blob `2020d4e2da6dea8601525203e7ab307d21c40a73` contains **eight** direct internal `codec.mutex_` guard sites; the header has no direct reference to `reservationMutex`, `g_MetadataLock`, or native `UsageLock` and the scoped `PublishBatch` path does not call back to the Runtime.

`InterpreterImage::ReserveImageBudget` takes `g_MetadataLock`, performs a codec stats query, and invokes `ReserveImages` (which takes reservationMutex then the codec mutex). `GetMetadataCapacitySnapshot` also holds `g_MetadataLock` while calling `GetMetadataCapacitySnapshotLocked`, which reads codec stats. Both paths preserve a forward metadata-to-codec dependency. The staged-batch and ordinary-placeholder publisher continue to reach `Runtime::PublishBatch`/`Publish` via their already reviewed call chains.

**Conclusion, deliberately narrow:** within this six-file pinned survey, no direct **codec mutex → reservationMutex** acquisition was observed. This is **not** a complete compiler CFG/call graph or proof there is no reverse edge in any other native module, callback, dynamic operation, allocator or OS lock. The source verifier rejects unreviewed changes to the six/eight acquisition census rather than silently declaring safety.

## 2. Cross-callback `UsageLock` exception-safety gap

`il2cpp_plus/libil2cpp/vm/AssemblyShadow.cpp@dc941907884b9a7f44ade6085d05f2e4a1a96d9e` has `TryBeginPublication` call **manual** `LockUsage()`. It keeps the flag held after returning `true`. Later, `PublishActive` calls `InterpreterAssembly::PublishStagedImagesBatch`, then performs an active snapshot release-store, and explicitly calls `UnlockUsage()` on normal success or returned failure. There is no context-owned RAII fallback across these callbacks. In the transitive path, standard-library mutex acquisition and future native callees cannot be assumed nonthrowing merely from a successful source-host test. If a C++ exception escapes after the manual acquisition, unrelated RAII mutex guards unwind but the usage flag is not automatically cleared.

**Finding LEASE-01 — OPEN / HIGH:** Exception-safe lock custody is not proved. This is a **potential** exceptional-exit issue, not an observed Unity failure or proof the current publish path throws. Replacing the manual flag with a scope-bound lease must be separately designed and reviewed before modifying actual `il2cpp_plus` code.

**Finding LEASE-02 — OPEN / HIGH, separate transaction integrity:** Releasing `UsageLock` on exception **does not make a partially published metadata index rollback-safe**. A throw *after* the codec's lifecycle stores but *before* `s_active` publication can leave an uncertain state; a source-only lease cannot decide to roll back, retry or accept. Any native correction needs an explicit before/after-irreversibility failure policy and terminal/restart receipt, without reusing a consumed Local Validation batch.
