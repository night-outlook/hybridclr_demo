## Source and measurement definition

The preceding [native population/lifetime review](B2_NATIVE_ENUMERATOR_POPULATION_LIFETIME_REVIEW_2026-11-17.md) proved from pinned source that `il2cpp_class_for_each` is an initialized/visible/cache-based public class population, not an independent physical TypeDef population. The original V1 execution getter instead uses `Assembly::CaptureShadowEnumeration` → `CopyValidAssemblies` (nonzero **assembly** token, original physical registration order) → `GetAssemblyTypeHandle` and first-wins `images.emplace(handle,image)`.

This checkpoint tests **Lane P only:** sum the *physical TypeDef slot occurrences* represented by `image->typeCount` across every supplied token-valid physical image. Let `S = sum(image->typeCount)`. For an independently authenticated, complete snapshot of this physical image registry, `S` is a conservative **upper bound on distinct metadata TypeDef handles with a first-owner in that registry**. It is **not** the number of unique handles or the number of TypeDefs used by observed execution classes: distinct handles may be duplicated across physical images, and many physical definitions may never be instantiated or referenced. This is not a bound for handles outside that eligible original-V1 registry, nor proof of original V1 field15 parity.

### Why the original physical scanner matters

The standalone host compiles and executes the **actual** `il2cpp_plus/libil2cpp/vm/AssemblyShadowOriginalV1ImageScan.h` at Git blob `41cdb90776f1f68f3fc7cbff85045965e29b99b0`, checked out from native commit `cecf4b859d50b128e5c0fc6c90cd89e3a452b96a`. Its `Scan` rejects malformed image/backlinks and preserves the token-valid physical assembly order, **including interpreter images and zero-TypeDef images**. `image->token==0` is deliberately **not** treated as the `CopyValidAssemblies` eligibility predicate; the assembly token is.

The native image scanner still requires an independently admitted initial metadata Reader and the existing `g_MetadataLock` plus its internal `s_assemblyLock` for actual borrowed image lifetime. Synthetic host input and source-pin verification cannot provide those guarantees.

## Implemented, isolated code and boundaries

Three new files exist **only** in `hybridclr_demo`:

- `Tools/AssemblyShadow/R03IR/TypeDefCensus/PhysicalTypeDefSlotUpperBound.h`: test-only `Census` with explicit `Prepare`, `ObserveFirst`, `BeginSecond`, `ObserveSecond`, `SealWithinSourceScope`, `MarkUncovered`, `Snapshot`, and `Release`. `Prepare(maximumImages,slotBudget)` allocates its bounded image-fact array before a prospective metadata lock. Both image passes use O(1) per callback and no heap allocations, text operations, class creation or TypeDef dereferences. It retains opaque image/assembly identity values **only inside the prospective source-protection window** and scrubs them at successful seal or any failure. Two complete, ordered and scalar-identical image passes are structurally required; they do not establish a coherent VM/class/GC epoch.
- `Tools/AssemblyShadow/R03IR/TypeDefCensus/PhysicalTypeDefSlotUpperBoundHost.cpp`: synthetic original-physical-source fixture, strict checked assertions and explicit complete/incomplete JSON output. This is a standalone host driver, **never a Unity/native compilation roster member**. A test validates the full 1,024-image boundary and fail-closed 1,025th image; another accepts `uint32_t`-maximum per-image slot count within a caller-specified 64-bit budget, without artificially clamping to native B2's 8,192 per-image TypeDef lookup cap.
- `.github/workflows/r03-b2-physical-typedef-slot-host.yml`: macOS/Linux × C++11/C++17 strict+ASan/UBSan CI; exact commit/blob checks for the original native scanner; compiles the host with the real pinned helper and asserts both JSON fixture results preserve false production/epoch/acceptance flags.

**Data contract:** `firstPassSlotOccurrences`, `aotSlotOccurrences`, `interpreterSlotOccurrences`, zero-TypeDef images, per-image maximum and observed 128/1,024/per-image-8,192 threshold flags are reported as **synthetic source observations** only. A failed/partial first pass may retain the observed slot count as diagnostics, **not** an accepted upper bound or a lower bound on unique handles. Only a complete two-pass supplied inventory sets `reportedUpperBoundForSuppliedInventory=true` and a `possibleDistinctFirstOwnerHandlesUpperBound` value; `sourceOriginAuthenticated`, `originalPhysicalEnumerationProven`, `coherentVmEpochProven`, `realUnity`, `nativeIntegrated`, `R03Accepted`, `ReadyForHumanReviewGate` and `capacityDecisionAuthorized` always remain false.

**Capacity and cost:** `maximumImages<=1,024` is a **prototype image-count limit**, not evidence that a real game's physical image count fits. First-pass slot budget is an independent caller-defined `uint64_t`; checked arithmetic and a budget error fail closed. On the 64-bit Primary host, the fully preallocated 1,024-record image array reserves **32,768 bytes** (`Census::ReservedBytes`), excluding allocator metadata, stack/VM resources and any real Unity/GC/metadata-lock costs. Failure scrub is O(configured image capacity); no claim of accepted lock latency or 32-bit ABI has been made.

## Primary review findings

- **SLOT-01 — host-only PASS:** The implementation uses the correct **original physical token policy**, includes interpreter and zero-TypeDef images, independently counts AOT/interpreter slot occurrences, preserves ordered two-pass scalar comparison, and rejects missing, changed, invalid or over-budget source without exposing borrowed pointers in its result.
- **SLOT-02 — OPEN / HIGH (source identity):** The host does not call the real `Assembly::TryVisitOriginalV1ExecutionImages`, acquire the actual Reader/`g_MetadataLock`, authenticate a fully enumerated assembly registry, or measure a real game. Even two identical image passes may omit an identical physical source element in both passes; caller-supplied `interpreter` flags and opaque identities are unverified.
- **SLOT-03 — OPEN / HIGH (lifetime):** `Reader.Epoch()==1`, `g_MetadataLock`, `s_assemblyLock` and repeated observations do not independently prove class/GC allocation epochs, metadata publication coherence, pointer provenance or ABA exclusion. Existing shutdown/assembly-list source semantics require a separately reviewed synchronization and lifetime contract before native attachment.
- **SLOT-04 — OPEN / HIGH (product relevance):** `S` is an **upper bound on possible distinct first-owner TypeDef handles in a complete eligible physical image inventory**, not a high-water count of actually used TypeDefs. A very large `S` cannot justify allocating that many exact TypeDef records, and a value over 128 does not prove the observed use graph exceeds 128. Lane U (separately authenticated, all-path observed-use/rejection census) remains open, as do the combined B2 128 distinct-handle cap, 64-byte declaration-name cap and 65,536 lookup budget.
- **SLOT-05 — OPEN:** No Unity 2022.3 native TU, Player, real lock/stack/RSS/allocator/GC profiling, complete original V1 fields14/15, native V2 artifact/envelope, independent readback receipt/first recovery, or full R03 historical acceptance and Human Review Gate approval.
